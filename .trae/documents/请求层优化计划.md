# 请求层（request 目录）企业级基础治理优化计划

## 1. 目标与成功标准
- 面向真实业务：请求层具备稳定、可维护、可扩展的工程化基础（类型闭环、错误统一、鉴权一致、URL 规范明确）。
- 成功标准：
  - `src/api/**` 调用请求层时不会再出现 `/api/api/...` 拼接风险。
  - `request.get/post/...` 的 TypeScript 类型与运行时返回值一致：对外返回 `ApiResponse<T>`（与你的选择一致）。
  - 业务错误与 HTTP 错误对外统一成同一种错误形态（可用 type guard 识别），调用方不再需要同时处理 `res` 与 `axios error` 两套结构。
  - 鉴权策略一致：Bearer Token 场景下默认不携带 Cookie（`withCredentials: false`），并支持按请求覆写。
  - 401 / token 过期能够统一触发“清 token + 引导登录”的同一条路径（企业级闭环），同时保留可插拔能力（未来可替换为跳转/刷新 token 等）。

## 2. 当前状态分析（基于仓库现状）
- URL 风险：axios `baseURL` 固定为 `'/api'`，但调用方传入路径仍是 `'/api/v1/...'`，存在二次拼接风险。
  - `src/request/core/axios.ts`
  - `src/api/user/index.ts`、`src/api/video/index.ts`
- 类型不闭环：响应拦截返回 `response.data`（`ApiResponse`），但 `RequestPromise<T> = Promise<T>` 让调用方误判为拿到 `T`。
  - `src/request/types.ts`
  - `src/request/core/interceptor.ts`
- 错误形态不统一：业务错误 `reject(res)`；HTTP 错误 `reject(error)`。
  - `src/request/core/interceptor.ts`
- 鉴权策略混用风险：Bearer Token 同时开启 `withCredentials: true`。
  - `src/request/core/axios.ts`
- 自定义配置字段落地不足：`RequestConfig` 定义了 `showError/loading/cache/dedupe/retry` 等，但当前未实现。
  - 本次范围选择“基础治理”，不补齐这些能力，仅把类型与结构治理好，为后续扩展预留接口。

## 3. 方案与改动清单（按优先级）

### 3.1 统一 URL 规范（修复 /api 重复拼接）
**决策（来自你的选择）**
- 保留 `baseURL = '/api'`
- 调用方统一传 `'/v1/...'`（去掉前缀 `/api`）

**具体改动**
- 修改 `src/api/user/index.ts`：`'/api/v1/auth/login'` -> `'/v1/auth/login'`
- 修改 `src/api/video/index.ts`：`'/api/v1/video/list'` -> `'/v1/video/list'`
- 全项目检索 `request.get('/api/` / `request.post('/api/` 等，并批量修正为 `'/v1/...'`（以实际匹配结果为准）。

### 3.2 类型闭环：请求层对外返回 ApiResponse<T>
**决策（来自你的选择）**
- 对外返回完整 `ApiResponse<T>`，不在请求层剥离 `data`

**具体改动**
- 调整 `src/request/types.ts`
  - `RequestPromise<T>` 改为 `Promise<ApiResponse<T>>`（或引入 `RequestResult<T>` 并统一使用）。
  - 统一 `RequestConfig` 继承的 axios config 类型，避免把 `InternalAxiosRequestConfig` 暴露给调用方（更符合 axios 使用习惯）。
- 调整 `src/request/request.ts`
  - `get/post/...` 的返回值泛型与 axios 实际返回保持一致，确保 TS 推导正确。
- 调整 `src/request/core/interceptor.ts`
  - 响应成功路径保持 `return res as ApiResponse<T>`，但让类型声明能正确表达这一点。

### 3.3 错误统一：业务错误与 HTTP 错误收敛为 RequestError
**目标**
- 调用方只需要识别一种错误结构，并能区分：
  - `kind: 'biz'`：业务失败（如 `status_code !== SUCCESS_CODE`）
  - `kind: 'http'`：HTTP 状态码错误（401/403/5xx）
  - `kind: 'network'`：断网/超时/无响应
  - `kind: 'cancel'`：请求被取消（AbortController）

**具体改动**
- 新增 `src/request/core/requestError.ts`
  - 定义 `RequestError`（class 或 discriminated union）与 `isRequestError` type guard。
- 重构 `src/request/core/error.ts`
  - 将 `handleBusinessError/handleHttpError` 从“console + UI 强耦合”改为“生成/抛出统一错误 + 可选触发钩子”。
- 改造 `src/request/core/interceptor.ts`
  - 业务错误：`throw new RequestError({ kind:'biz', code, message, response: res })`
  - axios 错误：解析 `error.response?.status`、`error.code`、`error.message`、`error.name === 'CanceledError'` 等，统一 `throw RequestError`

### 3.4 鉴权一致性：Bearer Token 默认不带 withCredentials
**决策（来自你的选择）**
- 鉴权采用 Bearer Token

**具体改动**
- 修改 `src/request/core/axios.ts`
  - `withCredentials: true` -> `withCredentials: false`
  - 保留调用侧通过 `RequestConfig` 覆写 `withCredentials` 的能力（axios 原生字段）。
- 修改 `src/request/core/interceptor.ts`
  - `Authorization` 赋值前避免重复读取 token（`getToken()` 调一次缓存局部变量）。
  - 当 `withToken === false` 时不注入 token。

### 3.5 可插拔的“登录失效处理”（企业级闭环但不把 UI 绑死在 core）
**目标**
- 401 / TOKEN_EXPIRED 能走同一条“auth 失效”处理路径（清 token + 引导登录）。
- 请求 core 不直接依赖具体 UI（store/modal），但默认行为保持与现状一致（不破坏体验）。

**具体改动**
- 新增 `src/request/plugins/hooks.ts`（或类似命名）
  - 暴露 `setAuthExpiredHandler(fn)` / `getAuthExpiredHandler()`（仅存函数引用）。
- 调整 `src/request/core/error.ts`
  - 在识别到 token 失效（业务码 TOKEN_EXPIRED 或 HTTP 401）时：
    - `clearToken()`
    - 调用 `getAuthExpiredHandler()?.(context)`
- 新增 `src/request/plugins/defaultAuthExpiredHandler.ts`
  - 仅在该文件里引用 `useLoginModalStore` 与 `LOGIN_MODAL_TITLE`，提供默认 handler。
- 调整 `src/request/request.ts`
  - 在入口处加载默认 handler（例如 `import './plugins/defaultAuthExpiredHandler'`），确保默认行为与当前一致。

## 4. 影响面与兼容性
- `src/api/**` 的 URL 前缀会统一修改为 `'/v1/...'`，后端路由需与当前 `'/api' + '/v1'` 组合保持一致。
- 调用方若曾把 `request.get<T>()` 当作 `Promise<T>` 使用，将在类型层面暴露问题；本次会以“对外返回 ApiResponse”统一后修复相关 TS 报错。
- `withCredentials` 默认关闭：若后端仍依赖 cookie，会导致鉴权失败；但你已选择 Bearer Token，预期不依赖 cookie。

## 5. 验证步骤（实现后执行）
- TypeScript 编译：`npm run build`
- ESLint：`npm run lint`
- 手工冒烟：
  - 打开页面触发 `getVideoList/login`，确认网络请求 URL 不含重复 `/api/api`。
  - 模拟 token 失效（清 token 或后端返回 401 / TOKEN_EXPIRED），确认能清 token 并弹出登录（默认 handler 生效）。
  - 在调用方 `catch` 中验证错误结构：可用 `isRequestError` 区分并读取 `kind/code/httpStatus/message`。

## 6. 已锁定的假设与决策
- 返回值：对外返回完整 `ApiResponse<T>`（已确认）。
- URL：保留 `baseURL=/api`，调用方传 `'/v1/...'`（已确认）。
- 鉴权：Bearer Token（已确认）。
- 范围：基础治理（类型/错误/规范/解耦钩子），不实现 `retry/dedupe/cache/loading` 这些能力（已确认）。
